# Gemini search sufficiency continuation — 2026-11-08

## Status

No production-ready solution has been demonstrated. The strongest alternative so far is to give the decision turn the full retrieved passage instead of only the annotated sentence span. Across two repeated paired trials this improved finalization modestly, while preserving all observed necessary searches. The effect is too small and the sample too narrow to adopt as a policy. Production code and defaults remain unchanged.

## Root-cause evidence

The production system prompt already asks Gemini to identify all required facts, finalize as soon as admitted evidence supports them, and search only for a specific unresolved fact. The function is available in `VALIDATED` mode and the application executes only the returned native call. Google documents that `VALIDATED` allows the model to return either a function call or a natural-language response while validating function arguments ([Gemini function-calling modes](https://ai.google.dev/gemini-api/docs/generate-content/function-calling)). Thus the application does not force the repeated search; the model selects it.

The earlier 40-question run found unnecessary searches in 14/28 complete answerable cases. The failure is uneven: production finalized 3/12 two-hop cases, 4/8 simple cases, and 7/8 three-plus-hop cases. In the inspected Wunna example, the model repeatedly asked for the award after evidence stated that Maung Wunna was a two-time Myanmar Motion Picture Academy Awards winner. The follow-up queries named the person and award, so these were relevant but redundant searches, not unrelated investigations. The source record uses the shorter title “Wunna” while its text gives the full name “Maung Wunna”; this makes the system’s identity-caution language a plausible contributor, but does not establish that it explains the wider 14/28 result.

The earlier harness had not saved the post-evidence search query. It now records each query and compares it with the annotated missing subject/relation and passage title. This is a lexical entity-plus-relation proxy, not a semantic relevance judge. A read-only post-hoc pass over saved queries found 28/28 retrieval-first incomplete searches targeted the missing annotated fact. In the two context trials, 35/36 incomplete searches matched both entity and relation; the one miss asked only for “Ernest I Anhalt Dessau,” omitting the missing death-date relation. This distinguishes useful gap-directed searches from searches that merely invoke the tool.

The same proxy initially classified the complete-evidence searches as redundant checks of facts already covered by the annotations: 19/19 in retrieval-first, 7/18 with sentence-only context, and 4/18 with full-passage context. No complete-case query in those runs was classified as unrelated to an annotated fact. These were annotation-dependent classifications, not human semantic judgments; the evidence-fixture audit below found four complete labels that need reclassification, so these historical counts should not be treated as validated semantic relevance rates.

The 3.1 probe sharpens this assessment. Its two-hop baseline correctly finalized; when only the search declaration gained a required `unresolved_fact` string, the paired response called the already-supported mother relationship unresolved and searched for that same relationship. The model therefore retained the relevant question subgoal and produced a relevant query, but failed to compare that subgoal against the evidence already in the tool response. This points more strongly to evidence sufficiency/entailment judgment than to loss of the original question or application-forced tool selection. It remains a one-case observation. Combined with the small but repeated full-passage gain, the leading cause is the model's recognition of whether the passage establishes a relation, made worse when the response contains only a narrow sentence span. The data do not establish a single root cause or a reliable fix.

## Evidence-fixture audit and corrected baseline

Reviewing the saved passages exposed an evaluation-label problem. Four answerable records labeled `complete` do not establish the requested fact under source-grounded answering: the simple and two-hop Ken Burns records mention “Brooklyn Bridge,” not his birthplace; the Anastasia case says Stefan Nemanja restored Hilandar Monastery, not that he died there; and the World and Time Enough case does not connect director Eric Mueller to the separate passage about Eric C. Mueller. These findings are recorded in `data/samples/evaluation/evidence_sufficiency_audit.json`. The audit is offline only and is never sent to Gemini.

The first post-hoc correction reclassifies those four rows as insufficient while preserving the model outputs. On the primary paired run, the original raw counts were 14/28 unnecessary searches for production and 11/28 for the conditional-description arm. After review, 10/24 and 7/24 searches, respectively, remain unnecessary; both arms searched in 38/38 reviewed insufficient cases. The conditional-description arm still has only 17/24 correct final decisions on answerable sufficient evidence (70.8%), below target. The four invalid rows were searches, so the correction removes false positives from the unnecessary-search count rather than converting unsupported answers into successes. The reproducible recalculation is `scripts/reclassify_gemini_sufficiency_audit.py`; its output is ignored under `reports/generated/gemini-search-sufficiency-live-20261108-3/reviewed-summary.json`.

The nominal 40-question suite has 28 answerable records but only 20 distinct final annotation triples: simple and multi-hop variants repeat the same target facts. It therefore does not meet the objective's minimum of 30 independent questions. The reported baseline and candidate numbers remain useful for historical comparison, but the suite needs additional independent facts and reviewed evidence before it can support a broad reliability claim.

Production decisions and both arms' shared initial search calls retain the model default; the native search declaration, `VALIDATED` mode, tool history, evidence, and response schema are unchanged. An initial exploratory pilot accidentally selected repeated target facts across simple and two-hop records and is not treated as independent evidence (`reports/generated/gemini-temperature-zero-pilot-live-20261108/summary.json`).

On the four cases with paired decisions, both production and temperature-zero finalized 0/4 sufficient-evidence rows, unnecessarily searched in 4/4, and searched on 4/4 incomplete rows. The missing-entity-plus-relation proxy matched 2/4 baseline queries and 3/4 temperature-zero queries. ### Separate evidence coverage audit

The evaluator now has an experimental two-pass candidate: after the native search result, a tool-free call receives only the original question and returned passages, then emits a schema-constrained coverage report with required facts, status, evidence IDs, and exact quotes. The actual decision turn receives that report as data and still has native `search_evidence` in `VALIDATED` mode. The verifier never receives reference answers. The plan counts each extra call, and the candidate's request, token, latency, quote, ID, and status metrics are recorded separately.

A bounded five-case 3.1 pilot used 29 requests across two simple facts, two two-hop facts, and one three-hop fact. The evaluator rejected the three-hop initial response because it returned multiple native calls; four questions yielded paired decisions and eight audits. In the raw fixture labels, the candidate finalized 2/4 sufficient rows versus 0/4 for production, with 2/4 unnecessary searches versus 4/4. Both searched in all 4/4 incomplete rows. One of the four nominally complete conditions was not sufficient in the `required_sentence` view: the span for Edmond T. Gréville ends at “26 May 1966” and omits “, Nice”, although the full source passage includes the death place. Reclassifying that condition as insufficient gives three valid sufficient conditions: the audit arm finalized 2/3 versus 0/3, made one unnecessary search versus three, and both arms searched in all 5/5 insufficient conditions. The two candidate answers were source-supported and cited E1; one equivalent award-name paraphrase failed the exact-string matcher, so surface-match accuracy was 1/2 despite 2/2 manually supported answers. No unsupported finals or invalid citations were recorded.

The coverage audit's status matched the raw fixture labels in 7/8 conditions, with zero unsupported exact quotes and zero invalid evidence IDs. It correctly identified sufficient Wunna and Maheen evidence and the missing conditions; on Kirill's wife it explicitly reported “sufficient,” but the decision model still requested another search. This shows that a correct audit does not reliably govern the native decision. Candidate prompt usage was 13,234 versus 10,765 tokens across the recorded rows (+23%); output was 1,076 versus 323 tokens. Mean total generation latency per condition, including the shared initial call and audit, was 10.34 seconds versus 7.28 seconds (+42%). This is a promising small signal with a material cost increase, not a production-ready fix. A repeat on the three valid simple/two-hop cases stopped after three requests with HTTP 504 on the first production decision and was not retried. Artifacts: `reports/generated/gemini-coverage-audit-pilot-live-20261108/summary.json`, `coverage_audits.jsonl`, and `reports/generated/gemini-coverage-audit-repeat-live-20261108/summary.json`.

### Embedding the audit in the native tool response

To test whether the decision model was ignoring an extra user message, a second candidate placed the same coverage audit inside the `FunctionResponse` JSON as `evidence_coverage_audit`. The audit call, evidence, tool declaration, call ID, prompt, schema, and native `VALIDATED` mode stayed the same; only report placement changed. The `search_evidence` function remained available on every measured decision.

On the same three repeated targets (Wunna award, Kirill's wife's cause of death, and Maheen Khan's profession), the embedded-audit arm finalized 2/3 sufficient conditions, matching the 2/3 result with the separate-message placement. Production finalized 1/3 in this repeat, compared with 0/3 in the prior trial, so stochastic baseline variation is substantial and the placement change itself shows no advantage. The embedded audit arm searched in both observed incomplete conditions; production did too. Its five audits matched all five raw fixture statuses, with no invalid IDs or unsupported quotes. A separate retry attempt on these same three cases failed with HTTP 504 before any decision and was not retried.

A two-question generalization slice then used new facts: John Donatich's publishing organization and the two-hop father/birthplace fact for Ioan S. Nenițescu. On the two valid complete-evidence questions, the embedded-audit arm finalized 2/2 and production 0/2; both emitted answers matched the expected values and cited valid evidence. On the one observed incomplete condition, both arms searched. The other incomplete pair ended in a candidate `ReadTimeout`, so it remains unmeasured. All four successful audits in that slice had correct status, valid IDs, and exact supported quotes. Across the two successfully measured embedded-audit runs, production finalized 1/5 sufficient rows and made four unnecessary searches; the candidate finalized 4/5 and made one unnecessary search. Both arms searched on all 3/3 observed incomplete rows; two more incomplete conditions were lost to timeout/deadline errors. The candidate emitted four supported, correctly cited answers; the baseline emitted one supported, correctly cited answer. This is a promising directional signal on five unique facts, with the first three repeated, but it is far short of broad validation.

Across these two runs the embedded candidate used 13,589 prompt tokens versus 10,942 for production (+24%), and 1,102 output tokens versus 345. Weighted mean total generation latency per decision condition was 15.15 seconds versus 8.08 seconds (+87%); the candidate makes one extra generation call, and service latency varied substantially. All nine audits that completed in the embedded runs, plus the audit saved in the separate-message repeat before its 504, were correctly classified with no bad quotes or evidence IDs. The useful performance signal does not outweigh the extra cost or limited sample; no production change is warranted. ## Alternative experiments

### Retrieval-first input, 68 requests

The experimental design supplied the pinned initial search results with the question on Gemini’s first turn. Gemini retained native `search_evidence` in `VALIDATED` mode for additional searches. The experiment completed all 68 decisions across simple, two-hop, three-plus-hop, contradiction, and empty-evidence conditions.

- Correct final decisions on complete answerable evidence: 9/28, compared with 14/28 in the saved production-history baseline.
- Unnecessary searches: 19/28, compared with 14/28 baseline.
- Necessary searches on incomplete/empty evidence: 34/34, with no premature final answers.
- The nine answers all contained the expected reference value, cited every required evidence ID, and had no unknown citation IDs.
- Category results: simple factual 5/8 finalized, two-hop 4/12, three-plus-hop 0/8. The three-plus-hop regression makes this architecture unsuitable in its current form.
- Incomplete-evidence follow-up queries matched a missing source title in 28/28 cases. Mean decision latency was 1.04 seconds; this excludes the earlier retrieval itself. The experiment consumed 70,898 prompt and 2,446 candidate tokens.

This approach removes the model’s initial query proposal and function-call response from the decision history, but did not improve sufficiency. It changes the history and prompt framing and may lose the model’s useful query planning; do not adopt it without a stronger retrieval-first design.

### Full source passage versus required sentence, two repeated trials

The paired sample used 9 answerable questions (3 simple factual, 3 two-hop, 3 three-plus-hop), each with complete and incomplete evidence, plus one contradiction and one empty-evidence control. It retained the production prompt, native signed call history, function declaration, response schema, and `VALIDATED` mode. Only evidence width varied. Each trial made 51 requests, including 11 initial native calls and 40 decisions; both trials completed without provider errors.

| Result across two trials | Required sentence | Full source passage |
|---|---:|---:|
| Final decisions with complete evidence | 11/18 (61.1%) | 14/18 (77.8%) |
| Unnecessary searches with complete evidence | 7/18 | 4/18 |
| Reference values in emitted answers | 11/11 | 14/14 |
| Required source IDs cited in emitted answers | 11/11 | 14/14 |
| Invalid citation IDs | 0 | 0 |
| Search when evidence was incomplete | 18/18 | 18/18 |
| Incomplete search queries matching missing title | 18/18 | 18/18 |
| Mean decision latency | 964 ms | 959 ms |
| Decision prompt tokens | 40,468 | 44,928 |
| Decision candidate tokens | 1,599 | 1,924 |

There were three paired improvements from search to answer and no answer-to-search regressions across the two trials. The gain was concentrated in the selected two-hop cases: full passages finalized 4/6 versus 1/6 with sentence-only evidence. Simple cases tied at 4/6 and three-plus-hop cases tied at 6/6. Full passages used about 11% more prompt tokens; measured latency was similar. On the same nine-question subset, the saved earlier production run finalized 6/9. The full-passage result averages 7/9 across repeated trials, only one additional finalization on that small subset. This supports evidence width as a real factor, but not a sufficient production fix.

Control behavior was mixed on the tiny controls: empty-evidence cases requested search in all four view/trial rows; conflict status was correct in three of four rows (one sentence-only row requested search). These controls need broader repeats before any change.

The production and candidate arms make separate initial calls so each signed native history is genuine; the candidate checklist remains in the original model call when evidence is returned. `search_evidence` remains available on every decision, and the checklist is not seeded from evaluation annotations or reference answers. ### Plain-text duplicate of native evidence response

This candidate kept the native `FunctionResponse` byte-for-byte equivalent in structure, retained the same call ID, system prompt, schema, `VALIDATED` mode, and available `search_evidence` tool, and appended a plain-text rendering of the exact evidence IDs, titles, and excerpts in that same user message. It added no summary, annotation, or reference answer. The hypothesis was that the model might compare evidence more reliably if it could read both the structured tool payload and its literal text.

Across the first two paired 3.1 runs (four complete/incomplete case pairs), both production and candidate arms finalized **0/4** sufficient-evidence decisions and searched in **4/4** insufficient-evidence decisions. Each arm made two redundant searches on complete evidence; both correctly searched on incomplete evidence, and the lexical proxy found both arms' incomplete queries targeted the missing fact in all observed cases. In the separate empty-evidence control, both arms searched (1/1 each) and the native tool remained available for every decision. A repeated Wunna complete-only trial again had both arms search redundantly (1/1 each). Thus the duplicate did not improve sufficiency decisions in these trials, while it increased prompt tokens by 4–13% per paired run (2,887 to 3,257; 2,428 to 2,552; and 1,647 to 1,748 in the repeat). Latency varied substantially and does not support a stable comparison. The sample is small and the incomplete-query scorer is lexical, so these are negative directional results, not a general performance estimate.

One Wunna incomplete-evidence row is a possible query-targeting signal: the duplicate arm named the missing award, while production asked “Who is Wunna?” The paired experiment's broader incomplete results did not replicate a systematic query-targeting benefit. ## Production suitability and next step

The retrieval-first design regressed overall. `AUTO` did not improve the matched full-passage subset. Full passages showed a favorable but small signal on Gemini 3.5, then a mixed effect on the partial Gemini 3.1 sample; one Ken Burns context-width sample was mislabeled and is now excluded from sufficiency conclusions. The goal checklist did not improve the observed paired sufficiency rate and sometimes named an incomplete or unrelated target. The identity-guidance hypothesis is untested. The latest 10-question simple-fact comparison favors the required-gap schema directionally, but it has not been repeated on those cases and has no completed multi-hop comparison. No candidate meets the success thresholds, so keep production unchanged.

The evidence coverage audit remains a positive but unreliable result. Across four embedded runs (20 completed decision conditions), it finalized 8/11 sufficient rows versus production 6/11, with 82% higher weighted latency; its latest mixed batch reversed direction on a two-hop case. The required-gap schema's first favorable result did not reproduce; temperature zero, stateless Interactions history, and answer-first framing also failed to improve sufficiency in their small pilots. A distinct native function-selection experiment now exposes `search_evidence` and `finalize_investigation` together on the decision turn. In its first three-fact 3.1 pilot, the explicit-finalize arm finalized 2/3 sufficient cases versus production 0/3 and searched in all 3/3 incomplete cases, with all three candidate queries manually rated direct to the missing fact. The candidate used 13% more prompt tokens and 42% more total generation latency. Production's sufficient finalization rate varied from 0/3 to 2/3 across earlier same-fact pilots with different initial histories, so the current paired result does not establish an improvement over a stable baseline. A same-slice repeat was attempted but Gemini returned HTTP 429 after the first initial request, before any decision, because the free-tier daily request quota was exhausted. This is promising early evidence but does not establish reliability. Keep production unchanged until a repeat and broader reviewed evaluation confirm the gain.

Production source review confirms the current flow preserves the native signed model call and matching function response, allows either a final or tool call in `VALIDATED` mode, and executes retrieval only after the model selects `search_evidence`. The tool response exposes queries, returned evidence, newly available and previously available IDs, and whether the search added no new evidence. No forced-search path was found. The new stateless Interactions comparison replayed full native history and tied GenerateContent at 0/3 sufficient finalizations, with 3/3 unnecessary searches in both arms; Interactions had 43% higher mean total latency per condition in this three-fact pilot. A decision-only answer-first instruction change produced 1/3 sufficient finals versus production's 2/3, while both searched in 3/3 incomplete cases. The explicit-finalize native function is a more promising change to the action-selection structure, but the repeat needs to wait for quota recovery. No production edit is made yet.

The first `ANY` pilot couples the explicit final tool with a mode/schema change, so a follow-up comparator now holds production `VALIDATED` mode and final JSON schema constant while exposing `search_evidence` and `finalize_investigation`. Its same-slice 15-request preview is ready at `reports/generated/gemini-explicit-finalize-validated-preview-20261109/plan.json`; no live request has been made because the daily quota remains exhausted. Four additional three-request previews prepare conflicting-evidence and empty-evidence controls for both `ANY` and `VALIDATED` variants.
