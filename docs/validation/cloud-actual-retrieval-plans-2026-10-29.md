# Actual Cloud SQL retrieval plans

Read-only diagnostic on 29 October 2026. No production data, schema, indexes, extensions or Cloud SQL settings were changed. `default_transaction_read_only=on` was verified, with a 30-second statement timeout. Two sequential executions each were run for semantic and lexical SELECTs through the existing Cloud SQL Auth Proxy; there was no concurrent benchmark traffic initiated by this investigation.

## Statement and configuration

The deployed service specifies `SERVING_CHUNKING_CONFIGURATION_ID=1`. Read-only lookup of that row produced `fixed_tokens`, 512 tokens, overlap 32. The application provider's existing profile is `gemini_developer_api`, `gemini-embedding-2`, 768 dimensions, `gemini_no_title_v1`, no normalization. The semantic statement was built by the current local `_search_statement()` with that configuration, a 768-dimensional vector read from an existing embedding, `owner_id=None` (shared scope), and limit 5. It uses an existing **document** vector, not a separately generated query embedding; no model call was made. The lexical statement was built from the same `_eligible_memberships()`, `_keyword_statement()` and `_hydrate()` used by `search_keywords()`, for `Pocket Money Stuart Rosenberg`, limit 5. No code from the deployed image was inspected, so equivalence of the current local SQL builder and that revision is not independently established.

The actual parameterized SQL generated by SQLAlchemy is available locally at [semantic SQL](../../.cache/cloud-query-review/semantic-sql.txt) and [lexical SQL](../../.cache/cloud-query-review/lexical-sql.txt). These files contain placeholders, not bound vectors or credentials. Sanitized JSON plans with numeric node data are in `.cache/cloud-query-review/`; bound values, source text and vector components were not saved. The four EXPLAINs use the exact generated statements and processed driver parameters, not handwritten approximations.

## Repeated observations

| Measurement | First | Second |
|---|---:|---:|
| Semantic server execution | 2,379.9 ms | 2,353.5 ms |
| Semantic EXPLAIN roundtrip, including network and plan transfer | 2,653.2 ms | 2,733.1 ms |
| Lexical server execution | 6,436.4 ms | 6,418.2 ms |
| Lexical EXPLAIN roundtrip | 6,661.4 ms | 6,561.4 ms |

Planning was 2.96–7.31 ms. Both samples were warm with respect to PostgreSQL shared buffers: root nodes reported zero shared-read blocks. This does not establish cold latency or a tail percentile. `EXPLAIN ANALYZE` adds instrumentation work; its roundtrip includes network, returned JSON plan transfer and driver work, and is not equivalent to the production retrieval operation. The approximately 2.15-second Cloud Run semantic SQL roundtrip is a different run, vector, connection and possibly application revision. The 2.35–2.38-second server observations demonstrate that server work can account for a substantial portion of that magnitude, but cannot be subtracted from the Cloud Run measurement or used to assign the difference to network or application work.

At `work_mem=4MB` and block size 8 KiB, the semantic root reported 7,734 temporary blocks read and 5,635 written; lexical reported 7,669 read and 5,569 written. Root buffer counts include child activity; do not sum them across nodes. Root shared-hit blocks were 2,857,183 and 2,512,797 respectively, reflecting repeated buffer accesses rather than unique blocks. The listed key/ownership/range indexes were used for lookup, but there is no persisted lexical index for the dynamic chunk substring and no vector ANN index in this plan. Exact cosine ranking remains a scan of eligible unique ranges.

Table statistics showed recent automatic analyses, although `n_mod_since_analyze` was nonzero for several tables. Those counters are estimates and do not establish why the planner estimated the materialized and derived joins so poorly. A manual ANALYZE or statistics/configuration change was not run.

## Evaluation of next directions

**A — SQL simplification, recommended first as a controlled experiment.** The evidence establishes expensive repeated eligibility construction and materialization, severe cardinality underestimation, spilling and many indexed probes. Use the saved statements/plans to compare equivalent query rewrites in an isolated representative database, including the actual distribution of 125,760 source occurrences, 57,899 unique ranges and multi-chunk plans. Candidates include narrowing intermediate rows further, reducing repeated CTE scans and anti-probes, and testing planner-friendly join shapes. Evaluate alternatives to computing `to_tsvector()` for every eligible canonical range separately; a persisted lexical index is a separate design decision. Compare exact ordered identities, scores, source spans and authorization across shared/private/deleted/current/incomplete/corrupt cases and concurrent snapshots. A local `work_mem` experiment may characterize spilling but does not by itself justify changing Cloud SQL configuration. Neither stale statistics nor any single rewrite is established as the root cause until tested.

**B — Transactionally maintained serving eligibility, for architectural review.** A version/configuration/profile readiness record could avoid revalidating the full plan and all required embeddings for every search. It requires a precise invariant and an approved migration/backfill. Readiness must be atomically set and invalidated with plan and embedding writes, changes to profile identity, activation and any operation that can make the underlying state incomplete; concurrent indexers and failed/unknown commits need explicit recovery semantics. Reads must still join authoritative documents for current version, deletion and trusted owner scope, and preserve per-version membership and source provenance. Direct or administrative mutations must not bypass the invariant. Shared Content and equivalent profile rows need a defined consistency policy. This adds write-path and operational complexity and potential stale-eligibility risk. The plans confirm repeated eligibility work is expensive, but do not isolate completeness validation alone from materialization, visibility, sorting and representative selection. Do not select or implement this design without approval and comparative testing.

Neither direction changes exact-content identity or replaces exact vector ranking with ANN. BM25, ANN, new tables and Cloud SQL settings remain separate approval decisions.
