On 2026-11-10, the Jolliffe question was sent sequentially, with no retries. The previous manual configuration probe returned HTTP 504 after 58.982 seconds with its 60-second SDK timeout. Saved sanitized results: `reports/analysis/gemma-adapter-comparison-2026-11-10/requests.jsonl` and `reports/analysis/gemma-provider-diagnostics-2026-11-10/requests.jsonl`.

The benchmark 504 is recorded as SDK `APIError` HTTP 504 / `DEADLINE_EXCEEDED`, rather than a local `TimeoutError`; its 33.77-second total includes orchestration and pacing. The server returned the 504, but its relationship to the configured 30-second deadline cannot be established from this trace. Similarly, the manual 504 near 60 seconds does not prove what component initiated the timeout. Minimal thinking failed in one controlled attempt, which does not establish that thinking is irrelevant in general. The HTTP 500 from a no-tools request means tool calling is not necessary for the failure. Provider availability, load, request configuration and SDK behavior remain hypotheses; no server-side root cause was confirmed.

Retries remain disabled. A bounded 500/502/503/504 retry may be useful, but it must reserve each provider RPC within the run budget, preserve the exact turn and native state without repeating retrieval, honor total deadline and cancellation, and preserve failed attempts and recovered outcomes in telemetry. HTTP 429 must not blindly retry exhausted quota. Existing wrappers budget logical generation calls and need coordinated changes before this is safe.

The evaluator no longer requires an unrelated Gemini model setting for a Gemma-only run, records the actual instantiated adapter class and records the actual investigation model in the generic model field for investigation-only runs. This fixes metadata and configuration dependency; it is not a proven cause of provider failures. Focused tests and lint pass. No production provider default, prompts, retrieval, or retry policy changed.
