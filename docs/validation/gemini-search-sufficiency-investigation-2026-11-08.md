# Gemini search sufficiency investigation — 2026-11-08

## Recommendation

Do not change the production search policy based on these experiments. The production adapter already gives Gemini a real choice between calling `search_evidence` and returning a final response: Google documents `VALIDATED` as permitting either a valid function call or natural language, whereas `ANY` requires a tool call ([function calling modes](https://ai.google.dev/gemini-api/docs/function-calling)). The repeated unnecessary searches therefore appear to arise in the model's sufficiency decision after it receives evidence, rather than from the application forcing another search. This is the best-supported explanation, not a proven single root cause.

A diagnostic-only change to the function description reduced unnecessary searches from 14/28 to 11/28 in the main run (21.4% fewer). It still searched unnecessarily in 39.3% of complete answerable cases, and it finalized correctly on only 23/34 sufficient-evidence decisions (67.6%). That improvement is too small and unstable to meet the brief's adoption bar. The production prompt, adapter, tool declaration, defaults, and runtime behavior remain unchanged.

A later, structurally different diagnostic gives a stronger but unreplicated signal: making `finalize_investigation` an explicit native function beside `search_evidence` yielded 2/3 sufficient finalizations versus production 0/3, with both arms searching in all 3/3 incomplete cases. The same-slice repeat stopped on the first decision due to the provider's daily quota. Keep production unchanged until repetition and broader review confirm that this is reliable.

## What was inspected

The production path is in `src/investigation_engine/infrastructure/generation/gemini_investigation_model.py` and `src/investigation_engine/application/investigations.py`. The model request includes the native `search_evidence` declaration with `VALIDATED` function calling and the production structured final-response schema. The application executes retrieval only after the model returns a `SearchEvidenceCall`; it does not force a search after a final response. Native signed conversation parts are retained in the real flow.

Earlier saved diagnostic artifacts provide corroborating examples. The A/B/E/F and I–S artifacts repeatedly show searches for already-supported facts, including repeat searches after a native function response. In contrast, the incomplete-evidence controls often search appropriately. Saved G/H artifacts were previews rather than actual call records, so they are not counted as live evidence here. See the prior decision reports linked from `docs/README.md`.

## Controlled evaluation

The new diagnostic harness is `scripts/evaluate_gemini_search_sufficiency.py`, with tests in `tests/unit/evaluation/test_gemini_search_sufficiency.py`. It uses the pinned 40-question sample suite and local reference corpus: 8 simple factual, 12 two-hop, 8 three-or-more-hop, 6 contradictory, and 6 unanswerable questions. Twenty-eight answerable questions were evaluated with both complete and intentionally incomplete evidence; conflict and empty-evidence controls were included. Each run keeps native function calling available in both arms.

The baseline uses the production prompt, tool declaration, and response configuration. The candidate changes only the diagnostic copy of the `search_evidence` description to tell the model to search when a specific relevant fact remains unresolved. Reference answers are excluded from model requests and used only after generation. The harness saves the native initial response, then submits the model's signed content with an equivalent function response containing prepared evidence. It records whether the model proposes a search or finalizes; proposed searches are never executed. Thus this isolates the decision policy from retrieval quality and retrieval latency.

### Main 40-question run

The main run made 176 successful generation requests: 40 initial native function-call requests and 136 paired decision requests (68 per arm). There were no retrieval calls, database calls, or provider/protocol errors. The native function remained available on all 136 decisions.

| Measure | Production baseline | Conditional description |
|---|---:|---:|
| Correct final/conflict on sufficient evidence | 20/34 (58.8%) | 23/34 (67.6%) |
| Unnecessary searches on complete answerable cases | 14/28 (50.0%) | 11/28 (39.3%) |
| Search when evidence was incomplete or empty | 34/34 (100%) | 34/34 (100%) |
| Unsupported final answers on incomplete/empty evidence | 0 | 0 |
| Invalid citation IDs in answer rows | 0 | 0 |
| Conflict correctly identified | 6/6 | 6/6 |
| Mean decision latency | 1,017 ms | 1,077 ms |

There were 14 baseline and 17 candidate answer outputs. Post-hoc checks found the expected reference value in all 31 outputs (allowing equivalent date ordering); every output cited all required passage IDs, and none cited an unknown ID. This is a surface-level reference match, not independent adjudication of every nuance. The conditional description moved six sufficient-evidence cases from search to answer and three in the opposite direction, for a net gain of three finalizations. With only 34 sufficient cases, uncertainty is broad: approximate 95% Wilson intervals are 42–74% for the baseline and 51–81% for the candidate. The candidate's 34/34 incomplete-evidence search result has a lower interval bound of about 90%, so this sample cannot establish a ≥95% reliability target.

The initial request was shared by both arms. Saved arm token totals include that shared initial usage, so they should not be summed across arms. Decision latency averaged about 1.02 seconds at baseline and 1.08 seconds with the description change. An investigation-equivalent decision sequence averaged roughly 1.90 and 1.96 seconds including the shared initial call; these are generation-only figures and exclude retrieval.

### Post-hoc evidence-support review

A manual review of the saved complete passages found four answerable records whose evidence did not establish the labeled answer: two Ken Burns birthplace records (Brooklyn appears only in “Brooklyn Bridge”), the Stefan Nemanja death-place record (the passage says he restored Hilandar Monastery, not that he died there), and the World and Time Enough director record (the corpus does not link director Eric Mueller to the separate biography of Eric C. Mueller). The offline review manifest is `data/samples/evaluation/evidence_sufficiency_audit.json`; it is never supplied to Gemini.

Reclassifying those four complete rows as insufficient changes the main run to 10/24 unnecessary searches for production and 7/24 for the conditional-description arm. Both arms searched on 38/38 reviewed insufficient cases. Correct final/conflict decisions are 20/30 and 23/30, respectively; among answerable sufficient rows alone, this is 14/24 (58.3%) versus 17/24 (70.8%). The candidate remains far below the ≥95% success target. Reproducible post-hoc counts are in `reports/generated/gemini-search-sufficiency-live-20261108-3/reviewed-summary.json`, generated by `scripts/reclassify_gemini_sufficiency_audit.py`. The original 14/28 and 11/28 values are retained above as raw annotation-based counts for provenance.

The 28 answerable records contain only 20 distinct final annotation triples because simple and multi-hop variants reuse the same target facts. The suite is 40 distinct question records, not 40 independent questions, and does not satisfy the required 30-independent-question evaluation. The reported metric remains a limited diagnostic; the case bank must be expanded and evidence-reviewed before broader reliability claims.

### Decision temperature alternative

The diagnostic evaluator now includes a model-configuration alternative that sets temperature to `0.0` on candidate decision requests only. It leaves the production arm and both shared initial calls at the model default; prompt, tool schema, native history, evidence, and `VALIDATED` function calling are otherwise identical. A corrected mixed sample selected five distinct targets across simple, two-hop, and three-plus-hop categories. The run made 21 generation requests and recorded 16 decision rows before rejecting one three-plus-hop initial response containing multiple native calls. On the four paired cases with decisions, production and temperature zero both finalized 0/4 sufficient rows, searched unnecessarily in 4/4, and searched in 4/4 incomplete conditions. The lexical missing-entity-plus-relation proxy matched 2/4 baseline queries and 3/4 candidate queries. Both arms used 10,769 prompt tokens including the shared initial calls; candidate output was 337 tokens at baseline and 328 at temperature zero. Mean decision latency was 3.48 seconds versus 1.93 seconds, but the sample is too small to support a speed or cost conclusion. Neither arm emitted an answer; the native search tool remained available in every measured decision. Temperature zero did not improve sufficiency in this pilot, and no three-plus-hop decision was measured. A preliminary selection that duplicated target facts across simple and two-hop records is retained as an artifact but excluded from independent-question estimates. Artifacts: `reports/generated/gemini-temperature-zero-mixed-live-20261108/summary.json` and `reports/generated/gemini-temperature-zero-pilot-live-20261108/summary.json`.

### Separate evidence coverage audit

A diagnostic two-pass candidate now asks Gemini, without tools, to map required answer facts to passage statuses and exact evidence quotes. The actual second decision request then receives that report as data while native `search_evidence` remains available in `VALIDATED` mode. The verifier sees no reference answer. Its generation and token/latency costs are counted separately, and audits are post-hoc checked against the fixture labels, evidence IDs, and exact quote spans.

One three-hop initial response contained multiple native calls and was excluded, leaving four paired questions and eight audits. In raw labels, the candidate finalized 2/4 sufficient rows versus 0/4 for production, and searched unnecessarily in 2/4 versus 4/4; both searched on all 4/4 incomplete rows. Manual review found one complete-labeled `required_sentence` span did not include the death-place evidence: the Edmond T. No unsupported finals or invalid citations were observed.

It identified the Wunna and Maheen complete excerpts as sufficient and the incomplete variants as insufficient. ### Conversation-history protocol and prompt framing

Production source review confirms that the final decision is a model choice: the system instruction explicitly permits finalizing when evidence establishes the required relations, `VALIDATED` mode allows either a native function call or a natural-language response, and retrieval runs only after a `SearchEvidenceCall`. The application resends the native signed model content and a function response with the matching call ID. The function response includes each query, results, newly available and previously available evidence IDs, and an explicit `no_new_evidence` flag. This review found no app-side forced-search path or mismatch in the tested history construction; the evidence representation already exposes whether a later search added any evidence.

The diagnostic `scripts/evaluate_gemini_interactions_sufficiency.py` compared the existing GenerateContent protocol against stateless Interactions (`store=false`) on the same three reviewed facts, prompt, tool, evidence, and native history. Both protocols finalized 0/3 sufficient cases, made unnecessary searches in 3/3, and searched in all 3/3 incomplete cases. Search proposals on complete evidence were confirmatory searches for facts already directly supported. Neither arm emitted an answer, so answer and citation quality could not be scored. Interactions used 7,829 prompt tokens versus 7,882 for GenerateContent; mean total latency per condition was 2.24s versus 1.56s (+43%). The API history alternative therefore did not resolve the behavior and added latency in this small pilot. This stateless test explicitly replayed the complete client-owned history; it did not use server-managed state. Google's [Interactions migration guide](https://ai.google.dev/gemini-api/docs/migrate-to-interactions) describes the client replay requirement for stateless mode and recommends Interactions for new development, but migration guidance alone is not evidence that it improves this decision.

A separate 15-request comparison changed only the opening paragraph of the decision instruction to an answer-first formulation. Initial requests, the remaining prompt, native signed history, evidence, final schema, and `VALIDATED` tool availability were held constant. Production finalized 2/3 sufficient cases and made one unnecessary search; answer-first finalized 1/3 and made two unnecessary searches. Both searched in all 3/3 incomplete cases. Emitted answers matched the fixture surface value with valid evidence citations; no unsupported final was observed. Prompt tokens were similar (7,910 vs. 7,874), while mean total latency per condition was 5.60s for answer-first versus 8.67s for production, a noisy service-time difference from only three facts. The prompt framing change did not improve sufficiency. Artifacts: `reports/generated/gemini-interactions-sufficiency-history-pilot-live-20261109/summary.json`, `reports/generated/gemini-interactions-sufficiency-history-pilot-live-20261109/manual-search-relevance-review.json`, and `reports/generated/gemini-answer-first-history-pilot-live-20261109/summary.json`.

Manual review across these pilots found all six sufficient-case searches to be reconfirmations of established facts. Among incomplete-case queries, four directly targeted a missing relation and two broad biography queries were plausibly useful; none were unrelated. This review shows why a binary “searched” metric and the current lexical missing-entity/relation proxy are insufficient measures of search quality. The decisions still failed at recognizing when the available evidence closed the question, even when a separate coverage auditor correctly labeled it sufficient.

### Explicit native finalization tool

A new diagnostic arm makes `finalize_investigation` a native function alongside `search_evidence` on the post-search decision. The candidate uses `ANY` to require the model to select one of those two functions; it does not force a final or remove the search option. It replaces only the structured natural-language final response for that decision with an explicit tool choice and finalization payload. Initial search requests, system instruction, native signed history, evidence, and final answer fields remain otherwise unchanged. The production adapter was not modified.

The first 15-request Gemini 3.1 Flash-Lite paired pilot covered three reviewed facts (one simple and two two-hop), with complete and incomplete evidence for each. Production finalized 0/3 sufficient cases and made 3/3 unnecessary searches; the explicit-finalize arm finalized 2/3 and made 1/3 unnecessary searches. Both arms searched in all 3/3 insufficient cases. Both candidate answers matched the reference values and cited valid evidence IDs; no unsupported final or invalid citation was observed. Manual review classified the candidate's one complete-evidence search as confirmatory and all three incomplete-evidence queries as directly targeting the missing fact. For production, all three complete-evidence queries were confirmatory; on incomplete evidence, two queries directly targeted the missing relation and one broad biography query was plausibly useful. The lexical scorer misses the candidate's Norwegian “født” (born) birthplace query, confirming the need for semantic review.

The candidate used 8,888 prompt tokens versus 7,874 for production (+13%). Mean total generation latency per condition was 6.98s versus 4.92s (+42%), with substantial per-request variability. This is a promising but very small one-trial signal, not an adoption result. The production arm varied across earlier same-fact pilots: it finalized 2/3 in the answer-first comparison and searched 3/3 in the stateless-history comparison; on the two overlapping complete cases in coverage batch 3, it finalized both. Those runs had different initial native search histories, so they are context, not direct paired repeats; they show that the current 0/3 baseline is itself unstable. A planned same-slice repeat stopped after two requests: Gemini returned HTTP 429 for the first production decision because the free-tier daily request quota had been exhausted. It yielded no repeat decisions and is not counted as evidence for or against the candidate. Artifacts: `reports/generated/gemini-explicit-finalize-native-tool-live-20261109/summary.json`, `decisions.jsonl`, `manual-search-relevance-review.json`, and `reports/generated/gemini-explicit-finalize-native-tool-repeat-live-20261109/summary.json`.

The first explicit-finalize pilot changes both the competing action set and function-calling mode (`ANY`, no final text schema), so it cannot identify which part produced the favorable signal. A second diagnostic policy now exposes the same two functions under production `VALIDATED` mode and retains the production final JSON schema, allowing either a `finalize_investigation` call or the usual structured text final. Its same-slice 15-request preview is `reports/generated/gemini-explicit-finalize-validated-preview-20261109/plan.json`. The API quota was still exhausted at the time this comparator was prepared, so it has not been run live. Four three-request previews also prepare conflicting-evidence and empty-evidence controls for both variants; the focused tests verify citation preservation and that search remains selectable. These controls should be live-tested before any production discussion.

### Repeat and control runs

A preplanned 20-question repeat slice stopped at 38/76 requests after a provider ServerError; there was no retry. Seven complete-evidence questions were paired: the baseline finalized 4/7 and candidate 5/7 (unnecessary searches 3→2). Both arms searched in all 7/7 incomplete cases. This is directionally consistent with the main run, but too small to validate the effect.

A separate 6-conflict/6-no-evidence control run completed 36 requests. Both arms searched after empty evidence in 6/6 cases. Candidate identified conflicts in 6/6; baseline did so in 5/6, with one malformed response. In the main run both arms identified all six conflicts. Valid conflict answers cited both conflicting source IDs in their nested claims.

### Evidence-width diagnostic

Because the pinned benchmark presents exact evidence spans, a separate experiment compared the required sentence alone with the full source passage. It covered six matched complete-evidence questions across two bounded runs, both of which stopped early on provider ServerErrors without retries. Full passages finalized 4/6 versus 3/6 for sentence-only evidence; three pairs finalized in both views, one moved from search to answer with the full passage, and two searched in both. The fuller view used about 26% more prompt tokens over those six decisions. This is too small to treat as a fix, but it shows evidence presentation is a relevant confound and the full passage is the more production-like input.

## Interpretation

The diagnostic-only function-description change produced a modest favorable shift, but no evaluated candidate has established a dependable fix. The required-gap field's favorable simple-fact result did not reproduce in a partial repeat; temperature zero, stateless Interactions history, and answer-first framing did not improve sufficient-evidence decisions. The embedded coverage audit's cumulative 8/11 versus 6/11 sufficient finalizations came with 82% higher weighted latency and a reversal on the latest two-hop case. Correct audit labels were sometimes ignored by the decision model. Manual review points to confirmatory searching after evidence is already sufficient, rather than unrelated query generation, as the recurring behavior. The explicit native-finalize function is the first one-call decision-structure alternative to show a substantial favorable shift (2/3 vs. 0/3), while preserving all observed incomplete-evidence searches; the repeat was blocked before any decision by quota exhaustion. It requires same-slice repetition and broader reviewed cases before it can be considered reliable. Evidence width remains a possible confound, but its sample is small.

No evaluated approach meets both the desired reduction in unnecessary searches and a strong answer/search correctness threshold. Keep the existing production behavior. The next experiment should target the identified decision failure with a genuinely different behavioral signal, measured on a repeated, manually reviewed paired slice across simple, two-hop, and three-plus-hop questions. It should score semantic usefulness of proposed searches through human review or a validated rubric, and include citation and unsupported-answer regressions while native function calling remains available. Avoid adding a second model call unless a one-call candidate establishes a clear gain first.

## Scope and limitations

- Main estimates are one live trial on a pinned 40-question local suite; generalization beyond these categories is unknown.
- Four complete-evidence labels were found invalid and post-hoc corrected; the original suite's 28 answerable records cover 20 distinct annotated target facts, below the requested 30 independent questions.
- Follow-up runs were incomplete because of Gemini ServerErrors; errors were recorded and not retried.
- Proposed searches were not executed. Search usefulness, retrieval precision, eventual resolution, and end-to-end investigation quality were not measured.
- The empty-evidence condition measures whether the model asks to search again, not whether it eventually returns `insufficient_evidence` after a real bounded retrieval loop.
- Answer checking verifies expected surface values and reference passage IDs, not a blinded human quality judgment.
- Context-width comparison has only six complete matched pairs.
- No production source/configuration was changed. No database or retrieval work, commit, push, or deployment was performed.
- Search proposals were not executed in the controlled decision pilots; semantic query review was manual and small. Retrieval precision and end-to-end resolution remain unmeasured.
- The four focused evaluation test modules pass 49 tests after adding control coverage for the explicit-finalize variants. Ruff lint and formatting checks passed on the changed evaluator/test files. Live candidates remain diagnostic-only and below the adoption threshold.
